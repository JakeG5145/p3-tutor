Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it lives in the model's context, in saved notes, or in a searchable manual, and say why.

Warm-up 2 min

Recall

A student asks, "Is the laser cutter free on Friday?" Without looking back: in the agent loop, what does the model output when it decides to use check_calendar, and what does the program do with the tool's result?

Check your answer

The model outputs a request naming the tool and its arguments; it does not run anything. The program runs the tool, then puts the result into the model's next input and calls the model again. That last step is today's topic: what exactly goes into that next input, and what happens when it gets too big.

The context window: what the model can see 5 min

Start with a concrete case. A student types: "How do I change the lens on the laser cutter?" Your program sends the model some text and gets text back. What text, exactly? Not just the question. It also sends the assistant's instructions, the descriptions of the tools, and any earlier messages.

The context window is all the text the model can look at when it writes a response, including the response itself. The Claude documentation calls it the model's "working memory", and separates it from the large body of data the model was trained on (Claude docs: Context windows).

Its size is counted in tokens: the small chunks of text a model reads and writes, often a short word or part of a longer one. You pay per token, and the window has a token limit.

The docs list everything that counts toward the window: the system prompt, every message including tool results, and your tool definitions. The output the model generates counts too (Claude docs). The system prompt is the standing instructions you write for the assistant, such as its role and rules.

Current Claude models list windows of up to 1 million tokens, which is roughly several long books. A big window does not mean you should fill it, as the next two sections show. Check the docs for the model you pick, because sizes differ by model.
A common mix-up

"A bigger window means the model remembers more, so I should paste in all the manuals." This is tempting because more information sounds safer. But the docs warn that as the token count grows, accuracy and recall degrade, an effect called context rot, so curating what is in context matters as much as how much space there is (Claude docs). Anthropic's engineering team describes the aim as "the smallest possible set of high-signal tokens" for the outcome you want (Effective context engineering for AI agents). Pasting every manual also means paying for every token on every call.

Check yourself

Your assistant has a 1,500-token system prompt and four tool definitions of 300 tokens each. A student has not typed anything yet. Roughly how many tokens of context are already committed on the first call?

Show the answer

About 2,700: 1,500 for the system prompt plus 4 × 300 for the tools. The docs list tool definitions among the things that count toward the window.

Between steps: everything is sent again 6 min

Here is the idea that surprises most newcomers. In the agent loop, each step is a separate model call, and the model does not carry anything over from one call to the next on its own. The "memory" within a task is created by your program, which sends the whole history again.

The Claude docs describe it this way: each turn's input contains all previous conversation history plus the new message, and the model's output becomes part of the input for the next turn (Claude docs). Your program keeps the list of messages; the model just reads whatever list it is handed.

Take one request, with made-up but plausible sizes. The student asks: "Is the laser cutter free Friday, and what settings do I use for 3 mm acrylic?"

  • The system prompt and tools are 2,000 tokens. The question is 50.
  • Call 1. Input: 2,050. The model requests check_calendar, about 50 tokens.
  • Call 2. The program adds the request and a 400-token calendar result. Input: 2,050 + 50 + 400 = 2,500. The model requests search_manuals (50 tokens).
  • Call 3. The program adds that request and a 3,000-token manual excerpt. Input: 2,500 + 50 + 3,000 = 5,550. The model writes the final answer.

Add up the input across the three calls: 2,050 + 2,500 + 5,550 = 10,100 tokens read, for a request whose useful content is much smaller. This is why a long agent run gets expensive faster than you might expect: each step re-reads all earlier steps. Tool results are usually the biggest items. (Prompt caching can make repeated parts cheaper; the docs note it changes what you pay, not whether the tokens count toward the window.)

A common mix-up

"The model remembers the calendar result from step 2 because it saw it." It does not. If the program forgot to include that result in call 3, the model would have no trace of it. The history is a list your code manages. This is also why a quiz-0001 style question like "how many times was the model called?" matters: each call pays for all the history again.

Check yourself

In the run above, a fourth tool call, check_training_record, returns a 200-token result before the final answer. What is the cheapest correct way to let the model use that result?

Show the answer

Append it to the history and call again. The model sees only its input, and it needs the question and earlier results to use the new one well.

Keeping the context small 4 min

If every call re-reads everything, then a long run both costs more and runs into context rot. Anthropic's engineering post says to treat context as "a finite resource with diminishing marginal returns" (Effective context engineering). Two simple tools help.

Clearing old tool results: once the model has used a 3,000-token manual excerpt and moved on, you can drop it from the history. The post calls this a light-touch form of compaction, and the docs list tool result clearing among their context editing strategies.

Compaction: near the limit, summarize the conversation so far and continue with the summary as the start of a fresh context. The post says the art is to keep what matters, such as decisions made and open problems, and drop redundant tool output.

Compaction loses detail by design. Anything that must survive it exactly, like a student's training status, belongs in saved notes (next section), not in a summary.

For your assistant, the cheap first move is simple: keep tool results short. Have search_manuals return a few relevant paragraphs instead of whole chapters.

Between sessions: notes as memory 6 min

Now the longer gap. A student finishes training on Monday, and comes back Thursday. When the Thursday chat starts, the context window is new. By default, nothing from Monday is in it. A model does not remember earlier sessions by itself.

A common mix-up

"The assistant talked with her on Monday, so it will know her training status on Thursday." It will not, unless your program saves something on Monday and loads it on Thursday. Persistent memory is something you build, and it is not automatic.

The simplest way to build it is notes: text stored outside the context window, in a file or database, that the agent writes during one session and reads in a later one. Anthropic calls this structured note-taking, or agentic memory, and gives the example of an agent keeping a NOTES.md file and picking up from it after its context is reset (Effective context engineering).

The Claude API has a ready-made version, the memory tool. It lets Claude "create, read, update, and delete files that persist between sessions". It works on the same loop you already know: Claude requests a file operation, and your application runs it against storage you control, then returns the result as a tool result (Claude docs: Memory tool). So the model does not touch the disk, and you decide where the notes live and who can see them.

Two design points matter for your budget and your reviewers. First, notes are cheap to carry: you load a short file instead of replaying a whole old conversation. Second, notes need care. The docs tell you to restrict the memory directory against path tricks like ../, cap file sizes, and expire old files (Memory tool). For a student's training status, you may well prefer not to let the model write it at all: your program can store it in a normal table, and load a one-line fact into the context when the student logs in. That is still "memory", with no model judgment involved.

Check yourself

The assistant notices that the 3D printer in Room B is out of service this week. Where should this fact go so that a different student, tomorrow, gets the right answer?

Show the answer

Save it to storage that every new session loads. Context and compaction both live inside one session.

Retrieval: finding the right page 5 min

The third kind of "memory" is not about the past at all: it is a store of knowledge too large for the window, like your machine manuals. A hundred pages of manual is tens of thousands of tokens, so you cannot, and should not, put it all in every call. Instead the assistant retrieves just the relevant pieces when a question needs them. This is retrieval, and in your design it is a tool, like search_manuals.

Anthropic describes the general idea as just-in-time retrieval: an agent keeps lightweight references, such as file paths or stored queries, and loads data into context only when needed, rather than loading everything up front. The same post notes the trade-off: it is slower than having the data preloaded and needs good tools, so a mix is often best, with a little preloaded and the rest explored on demand (Effective context engineering).

For a long manual, a common recipe is:

  1. Split the manual into chunks, short passages of a few paragraphs each.
  2. When a question arrives, the search tool scores chunks against the query and returns the best few.
  3. Those few chunks come back as the tool result and enter the context. The model answers from them.

Scoring comes in two main kinds. Keyword search (BM25 is a standard method) rewards exact words. Embedding search turns text into numbers so that passages with similar meaning score as close, even with different words. Anthropic's article on contextual retrieval gives a useful example: a query for an error code like "TS-999" can be missed by embeddings but found by exact-term matching. It also shows that a chunk often loses context when cut out, such as a passage that says "revenue grew 3%" without naming the company, and suggests adding a short explanation of where the chunk comes from before indexing it. In their tests, combining contextual embeddings with BM25 cut failed retrievals by 49% (Introducing Contextual Retrieval).

For the makerspace: a chunk reading "Set power to 40%" is useless unless it also says which machine, material and thickness. Tag each chunk with the machine and section title, such as "Laser cutter > Settings > 3 mm acrylic". That costs nothing at query time and improves matches on part numbers, setting names and model codes.

Check yourself

A student asks about "nozzle ZX-4412 clog". The manual has that exact code in one chunk. Which search is most likely to find it reliably?

Show the answer

Keyword matching, ideally combined with embedding search. Exact codes are what keyword search is good at.

Worked example and practice 5 min

Worked example

A student returns and asks: "Can I book the CNC router tomorrow? And remind me what bit I used last time." Decide where each piece of information comes from.

  1. List the facts needed. Router availability tomorrow; whether she is trained on the router; the bit she used last time; the router's safety rules for the answer.
  2. Availability changes constantly, so fetch it. Call check_calendar each time and let the result enter context. Saving it would go stale.
  3. Training status is a small fact that must be exact and last for months. Store it in a table the program reads at login, and put one line in the context. Exact, cheap, not subject to summary loss.
  4. The bit she used last time is a past-session detail. A note saved at the end of her last session, loaded at the start of this one.
  5. Safety rules sit in a long manual. Retrieve only the chunks for the CNC router with search_manuals, with machine and section tags on each chunk.
  6. Check the budget. Fixed context: prompt, tools, a few lines of status and notes. Variable: two tool results, kept short.
Your turn

A student asks: "Which sanding disc should I use on the 3D-printed part from last week, and is the printer I used still booked for me this afternoon?" Decide for each of these facts whether it is fetched live, loaded from notes, or retrieved from the manuals: (a) the booking, (b) which printer and material she used last week, (c) sanding guidance for that material. The first one is done: (a) is fetched live with check_calendar, because bookings change.

Show a solution

(b) is a note from her last session, loaded at the start, because it is about the past and the model does not remember earlier sessions. (c) is retrieved from the manuals with a tagged search, using the material name that (b) supplied. Notice that (c) depends on (b): the notes load first, then the search query uses what they said.

Summary 2 min

  • The context window is everything the model reads in one call: prompt, tools, history, tool results, and its own reply. It is limited and gets worse when overfilled.
  • Between steps, your program re-sends the history each call. The model remembers nothing by itself, and each step costs all earlier steps again.
  • Between sessions, nothing carries over unless you save it: notes in a file or table, loaded next time.
  • For big knowledge like manuals, retrieve a few relevant chunks on demand, using keywords plus meaning, with chunks labeled by machine and section.
