Context and memory: what an agent sees, keeps and looks up

By the end of this lesson you can say, for the makerspace assistant, what sits in the model's context at each step, what is lost when a session ends, and which of two tools — a notes file or a retrieval search — keeps what.

Objective O3: context and memory in an agent About 30 minutes Builds on: the agent loop (learning record 0002)
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits. Both are context-and-memory problems, and both decide your cost per request. At the design review you will be asked "what does the model see, and what does it remember?" This lesson gives you the answer.

The context window 5 min

Start with a concrete case. A student types: "Do I need training for the laser cutter?" Your program sends the model some text and gets text back. What text did it send? Not just the question. It sent your instructions to the assistant, the descriptions of your tools, and the question.

The context window is all the text the model can look at when it writes a response, including the response it is writing. Anthropic's documentation calls it the model's "working memory", and distinguishes it from the large body of text the model was trained on (Claude docs: Context windows). Text is measured in tokens, the small chunks of text (a word, or part of a word) the model reads and writes. A window has a fixed size in tokens, and everything in a request counts toward it: the system prompt (your standing instructions), every message, every tool result, your tool definitions, and the model's own output (same source).

Think of the window as the desk you are working at. Whatever is on the desk, you can use. Whatever is not on the desk, you cannot see, however much exists in the filing cabinet down the hall.

Two facts about the window matter for your budget and your design.

First, the model has no other view of the world. It cannot open the booking system or the manual PDF by itself. If a fact is not in the window, it is not available, unless it is in the model's training, which is general, may be out of date, and knows nothing about your makerspace. You noticed in your own chatbot use that it can state an outdated fact confidently; this is part of why.

Second, a bigger window is not automatically a better one. The documentation says that as the token count grows, accuracy and recall degrade, a phenomenon called context rot, so "curating what's in context [is] just as important as how much space is available" (Claude docs). Anthropic's engineering team describes the limit as an "attention budget": each new token uses some of it, so the goal is "the smallest possible set of high-signal tokens" that makes the right behaviour likely (Effective context engineering for AI agents).

Current Claude models offer windows of up to 1 million tokens, according to the same documentation. That is enough room for many whole manuals, and it tempts people to paste in everything. Cost and context rot both argue against it, as the next sections show.

A common mix-up

"With a big enough window, the assistant just knows everything I put in." It is tempting because "fits in the window" sounds like "understood". But fit is not focus: the more text sits in the window, the more the model's attention is spread, and the more you pay for tokens that did not help. A one-page answer buried in 300 pages of manual is harder for the model to find than the same page given alone.

What is kept between steps 6 min

You know the loop: the model asks for a tool, the program runs it, the result goes back, repeat. Now we zoom in on "goes back".

Take one request: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" Each trip around the loop is a separate call to the model. For each call, the program sends the model everything so far: the rules, the tool descriptions, the question, every earlier tool request and every earlier result. The documentation describes it exactly: each turn's input holds "all previous conversation history plus the current user message", and the response it generates becomes part of the input for the next turn (Claude docs).

This is the most important consequence for you: what is kept between steps is the whole growing transcript, and the program keeps it, not the model. The model does not hold a thought from one call to the next. Between calls, it holds nothing. The transcript is the only continuity, and the program rebuilds it each time. It is like a colleague who gets amnesia after every sentence but is handed the entire meeting notes before speaking again.

Why this affects your budget

Model usage is billed in tokens, and every call re-sends the stack. So the cost of a request is not "the size of the answer"; it is the sum of the input of every call. Long tool results are the usual culprit: a result of 3,000 tokens is paid for again by every call that follows it. The worked example below puts numbers on this. (Prices differ by model and change, so check the current pricing page rather than quoting a rate to your sponsor from this lesson.)

The API also offers prompt caching, which makes repeated beginnings of the stack cheaper to pay for. The documentation is careful to say that caching changes what you pay for those tokens, not whether they count toward the window (Claude docs). You do not need it for your first design.

What a long request does to the window

Because the stack only grows, a long task eventually fills the window. Two standard remedies exist, both described by Anthropic (Effective context engineering):

  • Clearing old tool results. Once the model has used a result, the program removes it from the stack. The post calls this "one of the lightest forms" of trimming.
  • Compaction. When the conversation nears the limit, the model summarises it, and a new window starts from that summary, keeping the important decisions and open problems and dropping repeated detail.

For a makerspace question that takes three or four steps, you will likely never need either. Keep your tool results short and the problem mostly does not arise.

A common mix-up

"The model remembers what it did in the earlier steps." It seems obvious because the answer at step 3 clearly uses step 1's result. But that works only because the program put step 1's result back into the input. If your program forgot to append a result, the next call would not know it existed. Continuity between steps is something your code builds.

What is kept between sessions: nothing 4 min

A session here means one conversation or one task, from the first message to the end. Now Sam, a student, chats with your assistant on Monday and completes the laser-cutter safety quiz in the chat. On Thursday, Sam opens a new chat and asks to book the laser cutter.

What does the model know about Monday? Nothing, unless your program puts Monday's information into Thursday's window. The model's training does not change when it is used; the window of Monday's session is gone once the program stops sending it. The Claude documentation describes the memory tool as a way for Claude to "store and retrieve information across conversations", and it treats that as something you add, which tells you the default is no carry-over (Claude docs: Memory tool).

So "memory" in an agent is not a property of the model. It is a design you build in the program: something outside the window that survives, and a way to bring the right part of it back inside. This lesson covers the two designs the mission needs: notes (for what the assistant learns about a student or a task) and retrieval (for looking things up in a large body of text).

Notes as memory 5 min

The simplest memory is the one you already use: write it down. In note-taking memory, the agent writes short notes to a place outside the window and reads them back later. Anthropic calls this "structured note-taking, or agentic memory", and gives examples such as an agent keeping a to-do list or a NOTES.md file; in one of their examples, an agent playing a game wrote notes like "for the last 1,234 steps I've been training my Pokémon in Route 1" and picked up where it left off after its context was reset (Effective context engineering).

Anthropic's memory tool is a ready-made version. Claude asks to view, create, edit or delete files in a /memories directory; your application carries out each request, and so you decide where the data actually lives and how long it is kept (Claude docs: Memory tool). This is the same tool-calling loop you already know: the memory is just another tool whose "result" is a file's contents. The documentation shows the start of such a session: Claude's first move is to view the memory directory, your program replies with the file list, and Claude then reads the relevant file.

Worked picture: Sam's visit

For the makerspace, a memory file might look like this:

/memories/students/sam.txt
- Passed laser cutter safety training on 3 Oct
- Prefers evening slots
- Booked laser cutter Fri 15:00 (confirmed)

On Thursday, when Sam writes "book the laser cutter", the assistant starts by viewing Sam's file. Now "training done" is in its window, with no need to ask Sam, and the booking can go ahead. At the end, the assistant updates the file with the new booking.

Rules for good notes

  • Save facts that will matter later and will not change quickly. A training date is good. "The laser cutter is free tomorrow" is a bad note: tomorrow it is wrong, and the calendar tool will tell the truth then.
  • Keep notes short. A note file is read back into the window, so it spends the same tokens as anything else.
  • Keep one source of truth. If the booking system says Sam is trained, the note should not argue with it. Prefer a tool lookup for anything another system owns, and notes for what only the assistant observes.
  • Protect the store. Your application runs every file operation the model asks for, so it must refuse paths outside the memory folder and cap file sizes. The documentation lists these duties, including path-traversal protection, as the application's responsibility (Claude docs: Memory tool). Student records also deserve thought about privacy and how long to keep them.
Notes help inside one long task too. The same documentation suggests writing progress to memory because "your context window might be reset at any moment", and pairing memory with compaction, so that what must survive summarising is saved as a note (Claude docs: Memory tool).

Retrieval as memory 5 min

Notes suit small facts. The manuals are different: hundreds of pages that nobody wants in every request. The answer to "how do I change the laser cutter's lens?" lives on one page.

Retrieval means finding the few relevant pieces of a large collection and placing only those in the window. The collection stays outside; each request pulls in a small slice. Anthropic describes the modern agent version as "just-in-time" context: the agent keeps lightweight references, such as file paths or search queries, and loads data into context at runtime using tools, rather than loading everything up front. They note a trade-off: runtime exploration is slower, and the agent needs good guidance not to waste context (Effective context engineering).

How a search tool finds the right page

This is the part your design review will care about. A retrieval tool takes a query and returns the best-matching pieces. There are two common ways to match, and many systems use both:

  • Keyword search matches the words in the question to the words on a page. It is simple, fast and good for exact names such as "Model X200 lens".
  • Meaning-based search (often called semantic search, built on embeddings) matches by similarity of meaning, so "the cutter makes a burning smell" can still find a page titled "Ventilation and fumes". You do not need to build this today; know that it exists and what it is for.

Before searching, you chunk the manuals: cut them into pieces such as one section each. Too big and each result wastes tokens; too small and a piece loses the context that makes it make sense. Keep the machine name and section title with each chunk so the model can tell what it is looking at. Anthropic points out that such metadata, even simple things like file names and folder structure, helps an agent judge relevance (Effective context engineering).

Finally, retrieval is a tool like any other. Its description must tell the model when to use it, and its result should be short: return the top few chunks, not the whole manual, because every token returned is re-sent in every later call (see the steps section).

A common mix-up

"Retrieval means the model has learned the manual." The model has not changed at all. Retrieval only puts a few pages into this one request's window. If the search misses the right page, the model cannot see it and may answer from general knowledge or guess. That is why testing the search itself, with real student questions, matters as much as testing the model.

Worked example and practice 5 min

Worked example: counting what a request costs

The question: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" Assume these illustrative sizes in tokens: rules plus tool descriptions 2,000; the question 50; each tool request 50; calendar result 300; the manual page returned by search 3,000; the training lookup 100. The final answer is not counted in input. How many input tokens are sent over all four calls?

  1. Call 1. The input is the rules and tools plus the question: 2,000 + 50 = 2,050. The model asks for the calendar.
  2. Call 2. The input is call 1's input, plus the calendar request (50) and its result (300): 2,050 + 350 = 2,400. The model asks for a manual search.
  3. Call 3. Add the search request (50) and the 3,000-token page: 2,400 + 3,050 = 5,450. The model asks for the training lookup.
  4. Call 4. Add the lookup request (50) and result (100): 5,450 + 150 = 5,600. The model writes the final answer.
  5. Total input. 2,050 + 2,400 + 5,450 + 5,600 = 15,500 tokens. The 3,000-token page appears in two of the calls (3 and 4), so it is paid for twice.
Your turn

Change the design so the search tool returns a 500-token passage instead of the 3,000-token page. Everything else is the same. Calls 1 and 2 stay as they were (2,050 and 2,400). Work out calls 3 and 4 and the total, then say what the saving teaches about tool results.

Show a solution

Call 3: 2,400 + 50 + 500 = 2,950. Call 4: 2,950 + 150 = 3,100. Total: 2,050 + 2,400 + 2,950 + 3,100 = 10,500 tokens, 5,000 fewer than before. The saving is 2,500 tokens in each of the two calls that carry the result. Lesson: a short, well-targeted retrieval result is cheaper on every later call, and it also gives the model less to wade through.

Summary 2 min

  • The context window is everything the model can see for one call, output included. It is the only thing the model can use, and it is limited and costs tokens.
  • Between steps, the program keeps the whole growing transcript and resends it every call. The model holds nothing, and each long tool result is paid for again by every later call.
  • Between sessions, nothing is kept unless you build it. Memory is a design: storage outside the window plus a way to bring the right part back.
  • Notes keep small, stable facts the assistant learns. Retrieval pulls a few relevant chunks from a big document store. Live facts come from tools.
