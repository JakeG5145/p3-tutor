Context and memory in an agent

By the end of this lesson you can say what an agent's model sees at each step, what survives between steps and between sessions, and decide, for the makerspace assistant, what goes in context, what gets saved as notes, and what gets retrieved.

The context window 6 min

Start with an everyday case. You ask a friend for help with a form, but your friend can only look at one sheet of paper. Everything they know about your problem must fit on that sheet. If you want to add something, something else must come off.

A language model works like that friend. The context is the set of tokens given to the model when it writes its next output (Anthropic, Effective context engineering). A token is a small piece of text, roughly a short word or part of a word. The context window is the maximum number of tokens the model can take in at once. It is the sheet of paper.

Two facts about that sheet matter for your design.

Fact 1: the model remembers nothing by itself

Each model call starts fresh. The model does not keep anything from the previous call. If it seems to remember your earlier message, it is because the program sent that message again as part of the new context. Anything the model should know must be on the sheet at the moment of the call.

Fact 2: more tokens cost more, and can hurt

You pay for the tokens you send, and for the tokens the model writes. So the size of the sheet is a cost, which is why it connects to your sponsor's budget. A bigger window does not make this free: it only raises the limit.

There is also a quality cost. Anthropic describes the model as having an "attention budget": as the context grows, the model's ability to recall details from it tends to weaken, an effect called context rot. Its advice is to treat context as a limited resource and aim for the smallest set of high-signal tokens that gets the job done (same source).

A common mix-up

"The model remembers our conversation." It is tempting because chat apps feel continuous. But the memory is the program's, not the model's: the app stores the messages and sends them again each time. If the program stops sending something, the model has no trace of it.

What is kept between steps 6 min

In the agent loop, every step is a separate model call. So "what is kept between steps" really means "what the program chooses to send again." In the simplest design, the program keeps a list of messages and adds to it: the question, each tool request, each tool result. At each step it sends the whole list. This growing list is the agent's working memory for one task, and it is the same thing as the conversation part of Figure 1.

Worked numbers: why the list is expensive

Here is a made-up but realistic run. The instructions and tool descriptions take 1,500 tokens. The student's question takes 50. The assistant needs three tools, then answers.

11,500 fixed + 50 question1,550
2call 1 + 50 request + 300 calendar result1,900
3call 2 + 50 request + 1,200 manual excerpts3,150
4call 3 + 50 request + 150 training record3,350
Total input over the run9,950

Notice three things. First, the total is far more than the final context of 3,350, because each call resends everything before it. Second, the 1,500 fixed tokens are paid four times. Third, the 1,200 tokens of manual excerpts, once added, are paid for in every later call, even though only the final answer needed them. (Some providers offer a way to make repeated, unchanged text cheaper; check your provider's documentation when you get to costs. This lesson stays with the idea.)

Three ways to keep the list from growing without limit

  • Clear old tool results. After the model has used a result, the raw text is rarely needed again. Anthropic calls clearing old tool results one of the lightest forms of compaction (source).
  • Compaction. When a conversation nears the window limit, summarize it and start a new context from the summary (source). The risk is that the summary drops a detail you needed later. The article suggests first making sure the summary keeps everything important, then trimming the extra.
  • Return less from tools. The cheapest token is the one that never enters the context. A calendar tool that returns only the free slots on one day beats one that returns the whole month.

What is kept between sessions: notes 6 min

Everything in Section 2 disappears when the task ends, because the program throws the message list away. Next week, when the same student comes back, a fresh context knows nothing about them.

The fix is external memory: information the program saves outside the context window, in a file or database, and loads back later. Anthropic describes the pattern as structured note-taking, where the agent "regularly writes notes persisted to memory outside of the context window" and pulls them back in at later times (source).

Everyday example

A shift worker leaves a handover note: "Printer 2 jammed Tuesday, fixed. Maria still needs laser training." The next person starts with a clean head and reads the note. The note is short, because it holds only what the next person must know. That is a good model of agent notes.

What the makerspace assistant could save

At the end of a session, the program (or the model, through a "save note" tool) writes a small record. For example, in Python:

{
  "student_id": "s1042",
  "trained_on": ["laser_cutter", "3d_printer"],
  "pending": ["band_saw_training"],
  "last_booking": {"machine": "laser_cutter", "date": "2026-11-12"}
}

At the start of the next session, the program loads this record and puts it in the context, a few dozen tokens instead of a whole old conversation. Now the assistant can say, "You are trained on the laser cutter but not the band saw."

Rules for good notes

  • Save facts, not transcripts. A whole conversation is long and mostly irrelevant. A few fields are cheap and exact.
  • Prefer the real source when one exists. If the booking system already knows the bookings, do not copy them into notes; read them with a tool when needed. A copy can go out of date, and then the assistant states an old fact confidently, which is the problem you noticed with chatbots.
  • Decide who writes. Letting the model write free-form notes is flexible but can record mistakes. Writing fixed fields from your own program is safer for things like training status, which must be right.
  • Think about privacy. Saved records about students are personal data. Save the minimum, and check your university's rules before you design this.
A common mix-up

"A bigger context window means the assistant remembers students across visits." It is tempting because the window feels like memory. But a window only holds what is sent in this call. When the session ends, the next call starts empty unless the program saved something and loads it. Window size and saved memory are different tools.

Retrieval: finding the right page 6 min

Your manuals are long. Say all of them together are 60,000 tokens. You could put them all in the context, but by Section 2 you know the cost: 60,000 tokens resent at every step, plus the risk of context rot. The alternative is retrieval: keep the manuals outside the context, and bring in only the pieces needed for this question.

The usual steps

  1. Split each manual into small pieces, called chunks, such as one section or a few paragraphs each. Keep the manual name and section title with each chunk, so the model can cite it.
  2. Index the chunks so they can be searched. Two common ways are keyword search (match the words) and embedding search (turn each chunk and the question into a list of numbers that captures meaning, then find the closest). Keyword search finds exact terms like "kerf" or "M12"; embedding search can match "how thick can I cut?" to a chunk that says "maximum material depth." Many systems use both.
  3. Search at question time: the model calls a tool such as search_manuals("laser cutter acrylic thickness").
  4. Return the top few chunks into the context, and let the model answer from them.

Anthropic describes a related idea, just-in-time retrieval: the agent keeps lightweight references, like file paths or stored queries, and loads data at runtime using tools, instead of loading everything up front. It notes the trade-off: it is slower than pre-computed retrieval, and a hybrid, with some data loaded up front and the rest retrieved as needed, often works best (source). For you, a hybrid might mean loading the student's note and the short safety rules at the start, and retrieving manual pages on demand.

A common mix-up

"Retrieval means the model has learned the manuals." It has not. Retrieval copies chunks into the context for this call, and they vanish when the call's context is dropped. The model's own knowledge is unchanged, which also means that if the search returns the wrong chunk, the model answers from the wrong chunk, and may sound sure about it. Chunk size and search quality are design choices you will test.

Worked example and practice 3 min

Worked example

A student returns and asks, "Can I use the vinyl cutter now?" Where should each piece of information live?

  1. Needs to be on the sheet for this question: the instructions, the tool descriptions, and the question. These are always in context.
  2. Student's training status: a small stable fact about one student. Save it as a note and load it at the start of the session.
  3. Is the vinyl cutter free now: changes constantly and lives in the booking system. Do not save it; call the calendar tool.
  4. The vinyl cutter's safety rules: long and stored in the manual. Retrieve the relevant chunk with the search tool, rather than loading the manual.
  5. After the answer: clear the raw tool results; keep only a one-line summary if the session continues.
Your turn

Sort these four things into context now, saved note, live tool call or retrieved chunk, and give a reason for each: (1) the student's name and training; (2) Friday's printer availability; (3) the filament-change steps; (4) the student's question itself. The first is done for you: (1) is a saved note, because it is a small stable fact about one student.

Show a solution

(1) Saved note, loaded at session start. (2) Live tool call to the calendar: it changes and has its own source. (3) Retrieved chunk from the 3D printer manual: long, stored elsewhere, needed only for this question. (4) Context now: the question is the input that starts the loop.

Summary 1 min

  • The model sees only the context window in each call and remembers nothing on its own; the program resends what matters.
  • Between steps, the message list grows and is resent each call, so tokens (and cost) add up; clear, compact or trim it.
  • Between sessions, only what the program saved survives: short notes, loaded at the start.
  • Retrieval keeps long documents outside the context and brings in just the chunks the question needs.
