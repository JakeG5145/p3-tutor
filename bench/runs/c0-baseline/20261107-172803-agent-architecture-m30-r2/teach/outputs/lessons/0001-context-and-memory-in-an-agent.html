Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it lives in the context window, in saved notes, or in a searchable manual store, and say why.

Why this matters for you

Your assistant must answer from long machine manuals, and it must remember each student's training status between visits. Both are context-and-memory decisions. They also set your cost: your sponsor's budget is spent mostly on what you put in front of the model at every step.

Check your answer

Your program runs the tool, not the model. The model only writes a request that names the tool and its arguments. The program then adds the result to the conversation and calls the model again. That last part is today's topic: what exactly gets sent in that next call, and what happens to it afterward.

The context window: what the model sees 6 min

Start with an everyday situation. You ask a friend to proofread your report, but your friend has a rule: they can only work from the pages you put on their desk right now. They never keep anything from earlier visits. If you want them to know about last week's feedback, you have to bring that page again.

A language model works like that friend. A token is a small chunk of text, often a word or part of a word, and it is the unit the model reads and writes. The context window is all the tokens the model can look at when it writes its next output, including the output itself. Anthropic describes it as the model's "working memory", and distinguishes it from the large body of data the model was trained on (Anthropic docs: Context windows).

So what goes on the desk? Everything in the request counts: the system prompt, every message including tool results, and your tool definitions. The output the model generates counts too (same source). For the makerspace assistant, the desk holds:

  • the system prompt, your standing instructions ("You are the makerspace assistant. Never book a machine for an untrained student.");
  • the tool definitions: the name, description and parameters of check_calendar, search_manuals and the others, which you wrote in order for the model to know what it can call;
  • the conversation so far: the student's messages, the model's earlier outputs, and every tool result that came back.

The window has a size limit, measured in tokens. Current Claude models have windows of up to 1 million tokens, depending on the model (Anthropic docs). That is room for several long books, so you might think the limit is no problem. Two facts in the next section explain why it still is.

A common mix-up

"The model remembers what I told it earlier." It feels true in a chat app, because the app resends the earlier messages for you. But the model itself starts each call with nothing except what is in the request. When a chatbot "forgets" something from last week, there is no bug: nothing put it back on the desk. Your assistant will behave the same way, so remembering is something you build.

Between steps: context grows, and so does the bill 7 min

Now connect this to the loop you already know. Each pass through the loop is a separate model call, and each call needs the whole desk again. Anthropic's docs describe it this way: each turn's input contains all the previous conversation history plus the new message, and the output becomes part of the input for the next turn (Anthropic docs).

So between steps, what is kept is exactly this: everything, appended in order. The model's requests, the tool results and the earlier answers all stay in the growing list that your program resends. Nothing is kept inside the model.

Two consequences matter for your budget and your design.

Consequence 1: you pay for the same tokens again

If the base is 2,100 tokens, call 1 sends 2,100 input tokens, call 2 sends 2,600, and call 3 sends 5,700, because a long manual page came back from search_manuals. The total is 2,100 + 2,600 + 5,700 = 10,400 input tokens, even though the final context holds only 5,700. A long tool result is billed again on every later call in that request.

Prompt caching can lower the price of tokens you resend unchanged, but Anthropic notes that it "changes what you pay for those tokens, not whether they count": cached text still occupies the window (Anthropic docs). It is a pricing tool, not a way to free up space.

Consequence 2: more context is not automatically better

Anthropic's docs say that as the token count grows, accuracy and recall degrade, a phenomenon called context rot, so curating what is in context matters as much as how much room there is. The engineering team adds that context is a finite resource with diminishing returns, and that the goal is the smallest set of high-signal tokens that gets the job done (Effective context engineering for AI agents). Think of the desk again: a few relevant pages help, and a desk buried under 40 pages makes the one fact you need harder to find, even if it technically fits.

A common mix-up

"A 1-million-token window means I can paste in every manual and stop worrying." It is tempting because the manuals do fit. But you would pay for those tokens on every step of every request, and the answer quality can drop as the window fills. A big window gives you room; it does not tell you what to put in it.

What to do when a run gets long

For a long run, the Anthropic engineering team describes compaction: when the conversation nears the limit, summarize it and start a new window with that summary. They add that clearing old tool results is one of the safest, lightest forms of compaction (Effective context engineering). For your assistant, that could mean replacing a 3,000-token manual page with one line, "Manual p. 12: laser cutter needs a trained operator; focus lens rated 50 mm", once the model has used it. The cost is that detail you drop is gone from the model's view, so keep what later steps need.

Most makerspace requests are short, with three or four tool calls, so you will rarely need compaction. It matters for design: cap the size of what tools return, and your requests stay cheap and accurate without it.

Between sessions: nothing is kept unless you keep it 6 min

A session here means one conversation: it starts with a fresh list and ends when the list is dropped. When Priya finishes the laser cutter safety training on Monday and comes back on Wednesday, Wednesday's session starts with only the system prompt, the tool definitions and her new message. The model has no idea she trained on Monday. This is the same rule as before, stretched across days.

The fix is to save facts outside the window and load them when needed. Anthropic's engineering team calls one version structured note-taking or agentic memory: the agent writes notes to storage outside the context window and reads them back at later times. Their examples include a to-do list and a NOTES.md file, and an agent playing Pokémon that kept notes on its progress and maps across thousands of steps and read them after its context was reset (Effective context engineering). Anthropic also offers a file-based memory tool for this purpose (same source; see also the memory tool docs).

In your assistant this takes two small tools. The names below are only a sketch:

save_note(student_id, text)   # write a fact to a file or database row
read_notes(student_id)        # load that student's notes into the context

Note the shape: storage is ordinary code you already know (a JSON file or a table), and the model's only job is deciding what to write and when to read. The model never "has" the memory. It reaches it through a tool, and the notes enter the window as a tool result like any other.

What to save, and what not to

Notes cost tokens too, every time they are loaded, so save the facts that will matter later and are small: which machines a student is trained on, their booking preferences, an open question you promised to follow up. Do not save raw tool output, like a whole manual page, since the manual is already stored and can be searched again. Also think about who can change a note. Training status decides whether someone may use a laser cutter, so it should be written by your program from a trusted record, and not just because a student said "I'm trained" in the chat.

A common mix-up

"Memory means a bigger window." A bigger window holds more of one session. It is discarded when the session ends, so it cannot carry Priya's training from Monday to Wednesday. Longer-lived memory needs storage outside the window plus a way to load it. The two answer different questions: the window is "what can the model see right now", the notes are "what do we still know tomorrow".

Retrieval: finding the right page in a long manual 6 min

The notes store holds small facts. The manuals are different: hundreds of pages, mostly irrelevant to any one question. Retrieval means fetching only the few pieces of a large store that are relevant to the question and putting just those into the window. It is memory in the sense of "knowledge we can look up", and the window stays small because most of the manual stays outside.

Anthropic's engineering team describes two ways to do it (Effective context engineering):

ApproachHow it worksMakerspace example
Before the model call (pre-retrieval) Your program searches the store first, often with embeddings (numeric fingerprints of text meaning), and adds the best matches to the request. Student asks about the laser cutter's lens. The program searches the manuals and puts the top three passages into the request before the model sees it.
Just in time The context holds light references such as file names or section titles, and the model uses tools to load what it needs when it needs it. The model sees a list of manual sections, calls read_section("laser-cutter", "lens-care") and gets one section back.

The article notes the trade-off: the just-in-time approach is slower than having data ready ahead of time and needs well-built tools and heuristics so the agent does not waste context, and it suggests a hybrid, as Claude Code does by loading a CLAUDE.md file up front and using search tools for the rest. For a manual set that rarely changes, such as yours, the article suggests a hybrid may fit better than going fully one way.

Either way, the lesson from Section 3 applies: retrieval returns a few pieces, not a whole manual, and what returns is added to the list you pay for on every later step. Good tool design means tools that return short, relevant passages. For manuals, splitting pages into passages of a few hundred tokens each, with titles, is a common step before search. Finding the best split and the best search is its own topic, and you will meet it when you build.

A common mix-up

"Retrieval means the model reads the entire manual to find the answer." The point of retrieval is the opposite: the search happens outside the window, and only the best few passages go in. If your search tool returns the whole 200-page manual, you have built an expensive version of pasting it all into the prompt.

Worked example and practice 8 min

Worked example

On Wednesday, Priya writes: "Book me the laser cutter Friday at 2 pm." Decide what is in the context at each point and where each fact comes from.

  1. Start of session. The program builds the first request: system prompt, tool definitions and her message. The model does not know she trained on Monday, because that session's window is gone.
  2. Model call 1. The model sees it needs her training status and requests read_notes("priya"). Your program runs it and appends the result: "laser cutter trained, Monday". The request grows by the size of the note.
  3. Model call 2. The model requests check_calendar("laser cutter", "Friday"). The result (a short list of free slots) is appended. Call 2 has resent everything from call 1 plus the note.
  4. Model call 3. The model requests book_slot(...) and the confirmation is appended.
  5. Model call 4. The model writes the final answer, "Booked for Friday at 2 pm", and the loop stops.
  6. End of session. The window is thrown away. If something new should last, such as "prefers afternoon slots", the program saves it with save_note first.

Cost check: say the base (system prompt, tools and Priya's message) is 2,000 tokens, and the note, the calendar result and the confirmation add 100, 300 and 100 (model outputs ignored for simplicity). The four calls send 2,000 + 2,100 + 2,400 + 2,500 = 9,000 input tokens. Had step 3 returned a 3,000-token manual page as well, calls 4 and the ones after it would each carry 3,000 more tokens, which is why small tool results keep requests cheap.

Your turn

A different student, Marcus, asks: "What settings should I use to cut 3 mm acrylic on the laser cutter, and can you remind me when my 3D printer training expires?" Plan the memory for this request. The first step is given:

  1. Given: At the start of the session, the window holds only the system prompt, tool definitions and Marcus's message.
  2. Which tool call finds the acrylic settings, and where do those settings live before the call?
  3. Which tool call finds the training expiry date, and why must it be a call?
  4. What would you save at the end of the session, if anything?
Show a solution
  1. Given: nothing about Marcus or acrylic is known yet.
  2. A manual search such as search_manuals("laser cutter acrylic 3 mm settings"). The settings live in the retrieval store, outside the window. Only the best passage should come back.
  3. read_notes("marcus") (or a training-records lookup). The expiry date was not in the window, and the model cannot know it, so it must be loaded as a tool result.
  4. Probably nothing new: the date already exists in the record, and saving the cutting settings would duplicate the manual. You could save "Marcus works with acrylic" only if it will help later sessions. Saving little is the cost-saving choice.

Summary 2 min

  • The context window is what the model sees in a call: system prompt, tool definitions, messages, tool results and its own output. If it is not there, the model cannot use it.
  • Between steps, the program resends a growing list, so long tool results cost tokens again on every later call, and a fuller window can lower accuracy (context rot).
  • Between sessions, nothing survives unless you save it: notes in a store outside the window, loaded by a tool.
  • Retrieval brings only the few relevant passages of a big store into the window, either before the call or just in time.

Say it in your own words: without looking, explain to a teammate why the assistant can answer from a 300-page manual but does not have it in its context, and how it remembers Priya's training on Wednesday.
